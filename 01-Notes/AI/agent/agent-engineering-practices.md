# Agent 工程实践

本笔记汇总 Agent 落地中的工程能力：**框架选型、开发挑战、多智能体、具身智能、安全对齐、A2A 协议、评估指标、微调**。

## 1. 主流 Agent 框架对比

### 1.1 LangChain vs LlamaIndex

二者哲学不同：

```
LangChain：通用 LLM 应用"编排"框架
   核心：Chains / Agents / Memory / Callbacks
   擅长：工作流构建，多工具协作

LlamaIndex：专注外部数据的"数据"框架
   核心：Data Connectors / Indexes / Retrievers
   擅长：RAG，知识库问答
```

### 1.2 选型决策表

| 项目特征 | 推荐框架 | 理由 |
| :--- | :--- | :--- |
| 复杂多工具 Agent | **LangChain** | Agent Executor + LCEL 编排能力强 |
| 高质量 RAG 系统 | **LlamaIndex** | 索引/检索策略丰富、深入 |
| 多智能体协作 | **AutoGen / CrewAI** | 内建多 Agent 通信机制 |
| 轻量级、低耦合 | **直接调 LLM API** | 避免框架开销和黑盒 |
| 生产级流式 / 状态机 | **LangGraph** | 显式状态机，可观测性强 |

### 1.3 应用场景举例

**LangChain 适合**：
- 通用研究助手（搜索 + 代码执行 + 计算器）
- 自动化客服（API 调用 + 工单系统）
- 复杂 RPA 流程

**LlamaIndex 适合**：
- 内部文档问答助手
- 财报深度分析工具
- 个人笔记问答（Notion / Obsidian）

二者也常**结合使用**：LlamaIndex 构建检索工具 → 接入 LangChain 的 Agent。

## 2. 复杂 Agent 的四大挑战

### 2.1 规划与推理的鲁棒性

**问题**：复杂多步任务下，Agent 容易迷失：

- 卡在重复的思考-行动循环
- 工具失败后无备用方案
- 过早判定任务完成

**对策**：
- 强化 [[agent-planning]] 能力（ToT/GoT）
- 加入循环检测、失败重试
- 引入 Reflexion 机制

### 2.2 评估的可靠性与可复现性

**问题**：
- 开放式任务难定义"正确"
- 动态工具（搜索引擎）使两次结果不同
- 人工评估贵且不可规模化

**对策**：
- 多维度指标（成功率 + 效率 + 鲁棒性）
- 模拟环境固化外部依赖
- LLM-as-Judge 自动评估
- 详见后文"评估指标"章节

### 2.3 成本、延迟、可扩展性

**问题**：单次复杂任务可能数十次 LLM 调用，成本几美元 + 延迟数分钟。

**对策**：
- 关键步骤用强模型，简单步骤用便宜模型（Model Routing）
- 启用 Prompt Caching（详见 [[agent-context-engineering]]）
- 并行化独立步骤
- 用更小的专用微调模型替代通用大模型

### 2.4 安全与可控性

**问题**：
- 权限边界难以严格控制
- Prompt Injection 风险
- 自主性带来不可预测后果

**对策**：详见后文"安全对齐"章节。

## 3. 多智能体系统（Multi-Agent System）

### 3.1 核心优势

| 优势 | 解释 |
| :--- | :--- |
| **分工专业化** | 每个 Agent 角色专精（PM / Coder / Tester） |
| **并行处理** | 子任务同时执行，缩短总时间 |
| **鲁棒性** | 单 Agent 失败可由其他接替 |
| **视角多样性** | 不同立场辩论，激发创新方案 |

### 3.2 新引入的复杂性

```
┌──────────────────────────────────────┐
│  通信协议    协调机制    社会动态     │
│     ↓          ↓          ↓         │
│  消息格式   任务分配    信任/冲突     │
│  共享状态   领导选举    联盟/背叛     │
│  一致性     资源争抢    信用分配     │
└──────────────────────────────────────┘
```

**五大新问题**：
1. 通信协议与语言（详见 A2A 章节）
2. 协调与协作机制
3. 社会行为与动态
4. 系统状态一致性
5. 信用分配（任务成败归因到哪个 Agent）

### 3.3 主流多智能体框架

| 框架 | 来源 | 特点 |
| :--- | :--- | :--- |
| **AutoGen** | Microsoft | 灵活的 Agent 对话编排 |
| **CrewAI** | 开源 | 团队/角色概念清晰 |
| **MetaGPT** | 开源 | 模拟软件开发团队 SOP |
| **LangGraph** | LangChain | 显式状态机驱动 |
| **Swarm** | OpenAI | 轻量级 Agent 交接（handoff） |

## 4. 具身 Agent（Embodied Agent）

当 Agent 从软件世界进入物理世界（机器人、游戏 NPC），出现五个本质差异：

| 维度 | 软件 Agent | 具身 Agent |
| :--- | :--- | :--- |
| **感知输入** | 结构化（JSON、表格） | 非结构化（像素、点云）+ 符号接地 |
| **状态可观测性** | 完全可观测 | 部分可观测 |
| **行动空间** | 离散、确定 | 连续、随机、有不确定性 |
| **时间维度** | 回合制、异步 | 实时、连续反馈 |
| **错误后果** | 可逆、有限 | 不可逆、可能物理伤害 |

**关键挑战**：
- **符号接地（Symbol Grounding）**：语言概念→物理实体的映射
- **传感器融合**：多模态输入（视觉+力觉+语音）整合
- **安全控制**：实时碰撞检测、紧急停止、力反馈限制

## 5. Agent 安全与对齐

### 5.1 六类保障方法

```
┌─────────────────────────────────────────────┐
│ ① 核心模型对齐                                │
│   RLHF / DPO / Constitutional AI            │
├─────────────────────────────────────────────┤
│ ② 工具和权限严格管理                          │
│   工具白名单 / 最小权限 / 资源限制            │
├─────────────────────────────────────────────┤
│ ③ Human-in-the-Loop（HITL）                 │
│   敏感操作前需人类批准                        │
├─────────────────────────────────────────────┤
│ ④ 沙箱化执行环境                              │
│   Docker / VM / 受限执行环境                 │
├─────────────────────────────────────────────┤
│ ⑤ 明确规则与护栏                              │
│   正则过滤 / 危险命令拦截                     │
├─────────────────────────────────────────────┤
│ ⑥ 持续红队测试与审计                          │
│   主动攻击测试 + 完整行为日志                  │
└─────────────────────────────────────────────┘
```

### 5.2 实践要点

- **最小权限原则**：只给完成任务所需的最少工具
- **HITL 触发点**：删除/支付/外发/不可逆操作
- **沙箱隔离**：所有代码执行必须在受控环境
- **审计链路**：每一步 Thought / Action / Result 都要可追溯

## 6. A2A（Agent-to-Agent）协议

### 6.1 定位

A2A 关注的不是单个 Agent 怎么实现，而是**不同来源、不同技术栈的 Agent 之间如何通信和协作**。

```
普通 Agent 框架（LangChain）→ "应用层"
                            构建能干活的个体
A2A 协议                     → "协议层"
                            构建个体间的通信规则
```

### 6.2 与普通框架的关键差异

| 维度 | 普通 Agent 框架 | A2A 协议 |
| :--- | :--- | :--- |
| 关注点 | 个体的实现 | 群体的交互标准 |
| 抽象层次 | 应用层 | 协议层 |
| 解决问题 | 如何构建一个 Agent | 不同 Agent 如何相互通信 |
| 类比 | "如何编写一个浏览器" | "HTTP 协议怎么定" |

### 6.3 A2A 需要定义的内容

- 消息的格式（如何打包请求/响应）
- 能力描述（声明自己支持什么）
- 任务委托协议
- 信任与验证机制
- 异步通信、超时、错误恢复

### 6.4 现状

- **Google A2A Protocol**（2024 提出）
- **MCP**（详见 [[agent-tool-use]]）虽然是 Tool 协议，但也朝着 Agent 互通方向演进
- 标准化仍在早期，未达成业界统一

## 7. Agent 评估指标

### 7.1 三大评估维度

```
┌──────────────────────────────────────────┐
│  ① 任务成功率 (Task Success Rate)         │
│     最终结果是否达成目标                    │
├──────────────────────────────────────────┤
│  ② 过程效率 (Process Efficiency)          │
│     成本 + 延迟 + 步骤数                   │
├──────────────────────────────────────────┤
│  ③ 鲁棒性与可预测性 (Robustness)           │
│     错误处理 + 一致性 + 安全               │
└──────────────────────────────────────────┘
```

### 7.2 具体指标

| 维度 | 指标 | 衡量方式 |
| :--- | :--- | :--- |
| **成功率** | Task Success Rate | 完成任务的比例 |
| **成功率** | Step-wise Accuracy | 每一步正确率 |
| **效率** | Cost / Task | 每个任务的 Token / API 费用 |
| **效率** | Latency | 端到端总耗时 |
| **效率** | # Tool Calls | 工具调用次数 |
| **鲁棒性** | Error Recovery Rate | 工具失败后能否恢复 |
| **鲁棒性** | Consistency | 同一输入多次的方差 |
| **安全性** | Red Team Pass Rate | 抵抗攻击的成功率 |

### 7.3 主流评估工具

- **AgentBench**：通用 Agent 评估基准
- **WebArena**：Web 操作场景
- **SWE-bench**：软件工程任务
- **GAIA**：通用 AI Assistant 基准
- **LangSmith / LangFuse**：生产环境追踪与评估

## 8. Agent 微调

### 8.1 为什么要微调

仅靠 Prompt 的 Zero-shot Agent 在复杂或专门领域中：
- 稳定性不足（同一输入可能不同行为）
- Token 消耗大（每次都要塞工具描述+示例）
- 慢（不能用小模型）

微调可以把"思考方式"和"工具用法"**烧进模型权重**。

### 8.2 微调的本质

不是简单的 (input, output) 对，而是教模型**完整的决策轨迹**：

```
(任务, 思考链, 行动序列, 观察序列, 最终回答)
```

这是一种 **行为克隆（Behavioral Cloning）**。

### 8.3 数据收集三种方法

#### (A) 教师模型合成数据（最主流）

```
1. 定义任务集 + 工具集
2. 用 GPT-4 等强模型作为"教师"在 ReAct 框架下执行任务
3. 记录完整 (Task, Thought, Action, Observation) 轨迹
4. 自动/人工过滤失败和低质量轨迹
5. 用筛选后的轨迹微调小模型
```

代表工作：**Toolformer**、**FireAct**、**Agent-FLAN**

#### (B) 人工编写或修正轨迹

- 高质量但成本高
- 适合关键场景的种子数据
- 通常配合教师模型扩展

#### (C) 真实用户交互数据

- 从生产 Agent 收集日志
- 加上人工标注（成功/失败）
- 用 RLHF 或 DPO 进一步优化

### 8.4 微调方法

| 方法 | 特点 |
| :--- | :--- |
| **SFT** | 直接学习教师轨迹 |
| **DPO** | 偏好优化，学好的 vs 差的 |
| **RLHF** | 复杂但效果好 |
| **LoRA** | 参数高效，适合小团队 |

## 9. 工程化最佳实践清单

构建生产级 Agent 时的检查项：

- [ ] 选定合适的框架（避免过度工程）
- [ ] 系统 Prompt 固化，启用 Prompt Caching
- [ ] 工具集精简，描述清晰，参数有 enum
- [ ] 实现 Scratchpad + 长期记忆分层
- [ ] 加入失败重试 / 循环检测
- [ ] 高风险操作有 HITL 确认
- [ ] 沙箱隔离代码执行
- [ ] 完整日志（Thought/Action/Result）可追溯
- [ ] 红队测试覆盖 Prompt Injection 等场景
- [ ] 建立离线评估集 + 在线监控
- [ ] 成本/延迟有预警机制
- [ ] 失败案例反馈到数据集，迭代微调

## 10. 学习要点

- ✅ 框架选型从"逻辑驱动 / 数据驱动"两条线分析
- ✅ 复杂 Agent 的四大挑战：规划、评估、成本、安全
- ✅ 多智能体优势明显，但通信和协调是新难题
- ✅ 具身 Agent 与软件 Agent 有五个本质区别
- ✅ Agent 安全是体系工程（模型+权限+HITL+沙箱+规则+审计）
- ✅ A2A 是协议层，与 LangChain 等不在同一抽象层次
- ✅ Agent 评估要三维度（成功/效率/鲁棒）
- ✅ Agent 微调本质是行为克隆，数据是"决策轨迹"
